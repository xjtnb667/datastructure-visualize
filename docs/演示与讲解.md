# 项目演示与讲解

**项目名称：** 算法可视化平台
**文档用途：** 演示讲解稿 + 常见问题应答手册
**阅读难度：** 全文不含需要编程基础才能看懂的内容
**项目形态：** **前后端分离**的 Web 系统 —— 前端（Vue 3 页面）+ 后端（Node 服务）+ 数据库（SQLite 一个文件）。
最初的第一版是**纯前端**（只有一个网页，所有算法都在浏览器里跑）；后来加上**用户系统和管理员系统**，
用户数据必须存在服务器上（不能只存在浏览器里），项目才变成了前后端分离的形态（详见第八章）。

---

## 第一章 · 这个项目是做什么的

一句话：**把算法的执行过程"拍成电影"，左边是剧本（代码），右边是画面（动画），你按一下"下一步"，电影就往前放一格，而且永远知道现在演到剧本的第几行。**

**这套东西本身不需要登录**：游客打开网页就能看全部 101 个算法（还能**自己输入一组数据**、**搜算法**）。在此之上，平台还带**用户系统和管理员系统** —— 注册登录之后可以把算法**收藏**、平台会替你记下**学习记录**、可以看自己的**学习报告**、给算法写**学习笔记**、还能**换一个自定义头像**；管理员有一个后台页面，可以管理用户和算法。这部分是后加的，用一句话概括就是：**看算法不需要账号，想把学习内容存下来才需要账号。**

**打开网址先看到的是一个"首页"**（地址 `#/`）：一行大字"算法可视化平台" + 一句说明 + 一个「**进入学习-->**」按钮，右上角是登录 / 注册。
点按钮才进下面的算法界面（地址 `#/learn`）—— **首页上没有那条算法选择器顶栏**（还没进算法界面，选择器没有意义），
但右上角的用户区保留着，否则游客在首页没法登录。首页那行规模数字（几个大类、几个算法）是**从代码里数出来的**，不是写死的。
地址的规矩：`#/` 首页、`#/learn` 算法界面、`#/favorites` 我的收藏、`#/admin` 后台；**空地址或写错的地址会自动回到首页**，不会白屏。

**算法界面分成四块：**

│  代码区                    │  动画区                           │
│  · 带行号的 C++ 源码        │  · 柱状图动画                     │
│  · 正在执行的那一行         │  · 颜色图例：                     │
│    整行深青底 #116A6E       │    蓝=未排序 橙=比较中             │
│    + 左侧亮青竖条 #33CCCC， │    红=交换/移动 绿=已就位          │

> 子类的先后就是**代码里的注册顺序**：选择器只把**相邻**的同名子类并成一组，所以同一个子类的算法在注册表里必须连着写。
> 现在子类总数是 **39 个**（这一轮新增了「背包问题」和「双串模型」两个），名字互不重复 —— "同名子类被别的子类隔开、界面上裂成两个同名标题"这个老毛病已经没有了
> （当年「分配类排序」被「选择类排序」夹断过，界面上冒出过两个「分配类排序」标题）。
> 小类标题的样子是**白色加粗 + 左侧琥珀色高亮条**（和"当前选中的算法"的蓝色系分开，标题一眼能扫到，又不抢选中项）。

顶部「线性表 / 插入 ▾」是**两级选择器**：点开之后左边一列是大类（线性表、栈、队列、数组与矩阵、串、树与二叉树、图、动态规划、查找、排序），**点一下大类，右边一列就换成该大类下的算法**，算法再按子类分组显示（小类标题是白色加粗 + 琥珀色高亮条）。加新算法、新大类、新子类都不用改这个选择器。选择器顶部还有一个**搜索框**：跨全部大类模糊搜算法名称和 id，↑ ↓ 选、回车打开（见第九章 9.3）。

**六种可视化形式**（柱状图 / 单元格表格 / 结点箭头图 / 通用格子板 / 树形图 / 网络图）由算法自己声明用哪一种，界面会自动切换 —— 这是"新算法不用改播放器"这条可扩展性要求的直接体现。

其中**柱状图、树形图、网络图这三种都支持"主视图 + 下方板子"**：算法的某一帧只要带上了板子数据，界面上就自动在主视图下面再接一块（树和图还能指定把板子放在上方），两种视图同时显示。这是后来新增结构类型时复用最多的一套机制 —— 计数排序要画"计数数组 + 输出数组"、基数排序要画 10 个桶，都是靠它才看得见的。

其中第四种「通用格子板」是后来加栈、队列、矩阵时提炼出来的：这些东西形状完全不同，但都能归结成**一组格子 + 若干命名指针**，差别只在格子怎么摆（竖排 / 横排 / 折行 / 环形）。所以只写了一个渲染器就覆盖了 18 个新算法 —— **播放器、代码面板、控制器、选择器一行都没改**。
**这一轮加动态规划时又验证了一次**：填二维表本质上还是"一组格子 + 命名指针"，所以那 3 个算法直接用了**通用格子板**里现成的网格布局（和画矩阵同一套），**一个渲染器都没有新增** —— 注册表里的渲染器仍然是那 6 种。

## 第二章 · 现场演示怎么做（照着做即可）

1. 双击项目文件夹里的 **`启动项目.bat`**，它会**先起后端（端口 3000）、再起前端（端口 5173）**，然后自动打开浏览器（网址 `http://localhost:5173/`）。这一步现在起的是**两个**服务，所以窗口里会看到两段启动信息（后端的"接口地址 / 数据文件"，前端的"Local: http://localhost:5173/"）。
   - **打开后第一眼看到的是首页**（地址 `#/`）：一行大字「算法可视化平台」+ 一句话说明 + 一个「**进入学习-->**」按钮，右上角是登录 / 注册区。
   - 补两句加分的：**首页刻意不显示算法选择器那条顶栏**（还没进算法界面，选择器没有意义；顶栏在首页由代码条件渲染隐藏），但右上角**保留了用户区**，否则游客在首页没法登录；首页上那行规模数字（"10 个大类 · 101 个算法 · 代码与动画逐帧同步"）**是从代码里数出来的**（读算法登记表的长度），不是写死的文案 —— 以后加算法它自己会变。
   - 顺手可以说一句地址的规矩：**`#/` 是首页、`#/learn` 才是算法界面**；**空地址或者写错的地址会自动回到首页**，不会白屏。点「进入学习-->」进算法界面（地址变成 `#/learn`）。
   - ⚠️ **进算法界面后是"空状态"，不会自动帮你选一个算法**（这是这一轮修的）：画面上只有一句「**先选一个算法开始学习吧**」和一个「**看看有哪些算法**」按钮（点了展开顶栏的选择器），代码区 / 动画区 / 图例 / 笔记面板 / 控制条**一样都不显示**；选了算法才全部出现。
     讲法："**以前一进学习界面就默认打开冒泡排序，而这一次"默认打开"会被学习记录当成一次真实学习写进数据库** —— 用户什么都没看，记录里却多了一条。这种 bug 界面上完全看不出来，所以我把它改掉了，并留了 **6 条常驻回归用例** 盯着它（见第十章）。"
2. 指着左上角说："左边是冒泡排序的完整 C++ 源代码，当前执行到第 1 行，**整行深青底 + 亮青竖条，代码是亮白色**（配色参考 Notepad++ 的深色主题）。右边是同一份数据 `[5, 2, 9, 1, 7, 3]` 的柱状图。"
3. 点 **下一步** 两次 —— 高亮跳到第 5 行，第 1、2 根柱子变成红色并交换了高度，解说栏写"5 > 2，交换 a[0] 与 a[1]"。**这是全场的核心看点。**
   - 补一句加分点：柱子的**颜色和高度都是平滑过渡**的，不是瞬间跳变。因为这两个量用的是同一个进度值驱动，所以"柱子长高/变矮"和"柱子变色"永远同时开始、同时结束。
4. 点 **上一步** —— 高亮退回第 4 行，柱子换回原样，统计里"交换次数"从 1 变回 0。**证明回退是真的回退，不是重新播放。**（回退时颜色同样是渐变回去的）
5. 点 **重置** —— 回到第 1 步、初始状态。
6. 点 **播放** + 切到 **4×** 速度 —— 自动播放到底，最后所有柱子变绿，解说"排序完成：共比较 15 次，移动/交换 8 次"。
7. 拖 **进度条** 到中间任意位置 —— 瞬间跳转，没有卡顿。
8. 把 **算法** 换成"选择排序"，再换"插入排序" —— 左侧代码整份替换，右侧继续同步。
9. 把 **数据规模** 换成 12，点 **随机数据** —— 说明算法不是写死的演示，任意数据都能跑。
10. **（查找演示）** 点顶部选择器 → 左列点 **查找** → 右列出现"顺序查找 / 折半查找"，选 **顺序查找**。
    - 图上多了一条**橙色虚线**，标着"目标值 9" —— 那就是要找的柱子高度。
    - 连点「下一步」：紫色指针一格一格往右移，**左边的柱子逐个变暗**（已经排除掉了），直到某根柱子变绿 —— 命中。
11. **（查找演示·重点）** 再换成 **折半查找**：
    - 连点「下一步」：第一次就把范围砍到 `[0,7]` 里的 `mid=3`，然后**直接把一半柱子变暗**；第二次再砍一半。
    - 一句话总结："顺序查找是一个一个试，折半查找是**每次排除一半**，这就是 `O(n)` 和 `O(log n)` 的差别。" 这是很好的对比素材。
    - 补充一句：折半查找要求数据有序，所以它在载入数据时会自动先排一次序，点「随机数据」也不会喂给它无序数组。
12. **（线性表演示）** 选择器 → 左列 **线性表** → 右列分成"顺序表 / 单链表 / 双链表 / 循环链表与环"四组。
    - **顺序表 · 插入**：右侧变成**单元格表格**（16 个格子，虚线格子是空位）。连点下一步，能看到元素从后往前**一个个后移**，然后新元素放进空出来的位置，底部"表长 n = 6 → 7"。
    - **顺序表 · 按位查找**：只要 4 步就结束了 —— 因为顺序表是**随机存取**，直接按下标取，O(1)。可以和"单链表 · 按序号查找"对比着讲：后者必须从头一个个走。
    - **单链表 · 插入**：右侧变成**结点 + 箭头图**。连点下一步，会看到新结点先"挂"在最后，然后依次执行 `s->next = p->next`（新结点接上后面）和 `p->next = s`（前驱指向新结点）—— **这两行顺序不能反**，反了后半段链表就丢了。
    - **双链表 · 插入**：结点下面多出一排**虚线箭头**（prev 反向指针）。插入要改 4 根指针，一步一步看得很清楚。
    - **循环链表与环 · 寻找环的入口**：结点图右侧有一条**绿色回头箭头**从尾结点绕回某个结点 —— 那就是环。连点下一步：先快慢指针相遇，再让一个指针回到表头、两个指针同速前进，最后在**环入口结点变绿**，底部提示"已找到环的入口（绿色结点）"。
13. **（可扩展性演示）** 说明：加一个新算法只要写一个文件 + 注册一行，选择器、播放器、代码面板、渲染器全都不用改 —— 线性表这一整套（14 个算法 + 2 种全新可视化形式）就是按这个方式加上去的。

## 第四章 · 核心难点：怎么保证"代码行号"和"动画"绝对同步

这是本设计的灵魂，也是读者会重点问的地方。

### 4.1 先说常见的错误做法（用来做对比）

很多人会这样写：

```
高亮第 5 行
等 300 毫秒          ← 用时间控制节奏
交换两个数据
高亮第 6 行
等 300 毫秒
```

这种做法有三个致命问题：

1. **"上一步"根本做不了**，因为时间只会往前走，不会倒流。
2. **一改速度就乱**：把 300 毫秒改成 100 毫秒，"等"和"动画"就会错位。
3. **行号和画面对不上**：行号写在代码里，画面靠动画自己算，两者是"各记各的账"，遇到打断就会对不上。

### 4.2 我们的做法：先拍完胶片，再放电影

打个比方：

| 电影比喻 | 项目里的对应物 |
| --- | --- |
| **剧本** | 算法源码（左边那份代码） |
| **导演按剧本一场一场拍** | 用生成器函数（Generator）一次性把算法执行完 |
| **胶片** | 步骤序列 `steps`（一个数组，每一格都存着这一帧的画面 + 对应的台词行号） |
| **放映机** | 界面。按"下一步"就是把胶片往后走一格 |

关键点：

- **胶片是提前拍好的。** 页面一打开，算法就已经从头到尾执行完了，把每一步的样子存成了一个数组。所以后面无论你是点下一步、上一步、拖进度条，都只是在**翻阅已经拍好的胶片**，而不是重新演一遍算法。
- **每一格胶片上同时写着两个信息：这一帧画面长什么样 + 对应剧本的第几行。** 这两个信息是**同一份数据的两个字段**，不是两个分别维护的东西。所以"行号和画面对不上"这件事，在结构上就不可能发生。

用技术语言说就是：**步骤序列是唯一的真相来源（Single Source of Truth），代码高亮和动画都是它的派生结果，二者互为"兄弟"而不是"因果"。**

### 4.3 四条保证（讲解时可以直接背）

**保证一：一格胶片 = 一个语义动作。**
算法的每一个可观察动作（一次比较、一次交换、一次标记）都恰好对应一个步骤。多了会导致"点两下画面不动"，少了会导致"高亮卡住不动"。所有算法的这条规则都由自动化测试守着。

**保证二：每一格胶片都是独立的一张照片，不是"指向同一份数据的指针"。**
这是最容易出错的地方。如果不拷贝，所有历史步骤都会指向同一个数组，那个数组被后续操作一改，**所有历史记录就全变成了最终结果**，"上一步"立刻失效。代码里每次记录都强制拷贝一份，并且有一条专门的测试盯着这个错误。

**保证三：全系统只有一个地方能改"当前第几步"。**
所有界面元素——高亮行号、柱状图、解说文字、变量、统计次数、进度条位置——全都是从"当前第几步"推导出来的，**没有第二个地方可以单独修改它们**。比如"当前高亮哪一行"不是一个可以独立赋值的变量，而是一个只读的计算结果。所以不存在"改了步骤忘了改行号"的可能。

**保证四：画面和代码高亮都不自己保存状态。**
渲染柱状图的函数是"纯函数"：给它第 N 步的数据，它就画出第 N 步的样子，仅此而已，它不记得自己上一帧画了什么。这条保证让"上一步"和"下一步"走的是完全同一段代码逻辑。

### 4.4 数据结构长什么样（不用看懂代码，看懂表格即可）

| 字段 | 含义 | 大白话 |
| --- | --- | --- |
| `line` | 源码行号 | 这一帧对应剧本第几行 → **决定左侧高亮哪一行** |
| `array` | 这一帧的数组快照 | 这一帧柱子分别多高 → **决定右侧画面** |
| `action` | 动作类型 | 初始/比较/交换/移动/就位/完成 → **决定柱子什么颜色、解说栏显示什么标签** |
| `indices` | 涉及的数组下标 | 哪几根柱子是"当事人" → **决定哪几根柱子变色** |
| `sortedIndices` | 已经就位 / 已经命中的位置 | 哪些柱子已经完成 → **决定哪些柱子是绿色** |
| `range` | 还在候选范围内的下标区间 | 查找时哪些柱子还有可能 → **区间外的柱子画暗**（"每次排除一半"就靠它表现） |
| `comment` | 一句话解说 | 显示在底部解说栏 |
| `vars` | 关键变量 | 显示 `i = 0, j = 0` 这样的小标签 |
| `stats` | 累计统计 | 显示"比较 15 次、交换 8 次" |

**注意 `line` 和 `array` 在同一个结构体里**——这就是"绝对同步"的技术依据。

## 第五章 · "上一步"到底是怎么做到的

**一句话：不是把算法倒着算一遍，而是把放映机的指针往回挪一格。**

胶片已经拍好了，一共 30 格。第 3 格的画面、第 3 格对应的行号、第 3 格的解说词、第 3 格的统计数字，全都存在数组里。

所以"上一步"做的事情就是：

```
当前格子编号 3 → 改成 2 → 界面自动重新推导出第 2 格的一切
```

- **速度**：瞬间完成，不需要重新计算（在计算机术语里是 O(1)，即"花的时间是固定的，和数据规模无关"）。
- **绝对准确**：因为第 2 格的画面就是当初拍下来的那一格，不存在"倒退算错"的可能。
- **可重放**：点 10 次下一步再点 10 次上一步，必然回到同一个画面。这一点有自动化测试专门验证。

**对比**：如果采用"反向执行算法"的思路去做上一步，就得为每个算法单独写一套逆操作（交换可以逆，但"比较"没法逆、递归没法逆、图遍历没法逆），既做不全也做不对。我们的做法对所有算法一视同仁。

**上一步动画为什么也平滑？** 因为画面上每根柱子的高度是一个可以插值的数字。从上一步的高度平滑过渡到当前步的高度，用的是和"下一步"完全相同的过渡函数，只是起点和终点调换。所以视觉上"柱子交换也退回去"。

## 第六章 · 为什么调速度不会导致不同步

因为**速度只影响两件事**：

1. 自动播放时，两步之间隔多久；
2. 单步动画的过渡时长（几百毫秒）。

**速度完全不影响步骤序列本身。** 0.5 倍速和 4 倍速下，那 30 格胶片逐字节完全相同。所以"调速度导致代码和动画错位"这件事，在本架构下**物理上不可能发生**——不存在"改速度时忘了同步某处"的代码路径。

## 第七章 · 系统分层

整个系统分**前端**和**后端**两块，一共六层。前端那四层是"放算法电影"的部分，后端那两层是"记住你"的部分：

```
【浏览器里 · 前端】
┌──────────────────────────────────────────────────────────────┐
│  表现层（界面）                                              │
│  CodePanel 代码高亮 │ CanvasPanel 动画 │ ControlPanel        │
│  UserMenu 用户区 │ AuthDialog 登录框 │ AdminView 后台        │
│              都只读同一份状态，自己不保存状态                │
└──────────────────────────┬───────────────────────────────────┘
│                           │ 只读                             │
┌──────────────────────────▼───────────────────────────────────┐
│  状态层（Pinia store）—— 两个互不干扰的"仓库"                │
│  ① 算法播放状态：全系统唯一可写的光标 currentStepIndex       │
│     （其余全部是由它推导出来的只读结果）                     │
│  ② 用户状态：当前登录的是谁 / 我的收藏 / 学习记录            │
│  ③ 笔记状态：当前算法的学习笔记                              │
└──────────────────────────┬───────────────────────────────────┘
│                           │ 一次性预计算                     │
┌──────────────────────────▼───────────────────────────────────┐
│  引擎层（engine）                                            │
│  把生成器跑到底 → 全量步骤序列 + 规范校验                    │
└──────────────────────────┬───────────────────────────────────┘
│                           │ 每个 yield 一个步骤              │
┌──────────────────────────▼───────────────────────────────────┐
│  算法层（纯 TypeScript，零依赖，和界面完全无关）             │
│  101 个算法，10 个大类（线性表 / 栈 / 队列 / 数组与矩阵 /    │
│  串 / 树与二叉树 / 图 / 动态规划 / 查找 / 排序）             │
├──────────────────────────────────────────────────────────────┤
│  纯逻辑层（core，不碰界面，可以被单独测试）                  │
│  report.ts 报告口径 / algorithmSearch.ts 搜索 /              │
│  manualInput.ts 手动输入校验                                 │
└──────────────────────────────────────────────────────────────┘
                           ▲
                           │ 只有"收藏 / 学习记录 / 学习笔记 / 算法元数据"走网络，
                           │ 算法本身和动画数据一步都不经过网络
                           ▼
【服务器上 · 后端】（4 个文件，零新增依赖）
┌──────────────────────────────────────────────────────────────┐
│  HTTP 服务层   server/index.mjs                              │
│  收请求、分发路由、给前端发静态网页文件                      │
├──────────────────────────────────────────────────────────────┤
│  业务接口层    server/api.mjs                                │
│  23 个接口：认证 4 / 用户功能 10 / 管理员 8 / 公开 1         │
├──────────────────────────────────────────────────────────────┤
│  认证层        server/auth.mjs                               │
│  密码加盐哈希、会话令牌、注册登录、角色校验、入参校验        │
├──────────────────────────────────────────────────────────────┤
│  数据层        server/db.mjs  +  data/app.db                 │
│  建表（6 张）、初始化种子数据、参数绑定查询                  │
└──────────────────────────────────────────────────────────────┘
```

**分层的价值**：
- 算法层完全不知道"界面"的存在，所以它可以脱离浏览器单独测试；界面层完全不知道"算法"是怎么写的，所以加新算法不需要改界面。
- **报告页是这条分层原则最直接的例子**：页面上每一个数字都由 `core/report.ts` 里的**纯函数**从"学习记录 + 算法登记表"算出来，那个文件不碰任何界面元素 —— 所以"算法不对"和"画得不对"是两件可以分开查的事，改图不会动口径、改口径不用碰图。
- 后端也**完全不知道算法是怎么算的** —— 它只管"谁是谁、谁收藏了什么、谁写了什么笔记"。算法一步都不经过网络，所以后端再慢也不会影响动画的流畅度（这是当初决定"算法必须纯前端跑"时留下的好处）。

## 第八章 · 用户系统与管理员系统

这一章讲后加的那一半：**账号**。读者不需要懂技术，按"为什么做 → 怎么做的 → 谁能干什么 → 有什么规矩"的顺序看即可。

### 8.1 为什么从"一个网页"变成了"前端 + 后端"

第一版是纯前端：一个网页，所有算法都在浏览器里跑，**没有任何需要保存的东西** —— 关掉页面，一切归零。

加上用户之后就不行了，原因很直白：

> **用户数据必须存在服务器上，不能只存在浏览器里。**

- 收藏、学习记录如果只存在浏览器里，换个浏览器、换台电脑、清一次浏览器数据就全没了；
- 更关键的是**管理员要能看到全体用户**（有多少人、谁被禁用了），这些数据不可能散在每个人的浏览器里；
- 还有一件事**只能在服务器上做**：权限判断。如果"是不是管理员"由浏览器说了算，那谁都能改自己浏览器里的数据冒充管理员。

所以项目变成**前后端分离**：

```
浏览器（Vue 3 页面）  ──HTTP/JSON──►  Node 后端  ──SQL──►  SQLite 数据库（一个文件）
```

浏览器负责"演算法"，后端负责"记住你"。**算法还是在浏览器里跑**，这一点没有变，所以动画的流畅度和同步机制都不受影响（见第四 ~ 六章）。

### 8.2 三个技术选型，以及为什么这么选

这三条是讲解时最可能被追问的，理由都只有一句话：

| 选择 | 理由（一句话） | 追问时的补充 |
| --- | --- | --- |
| **数据库用 SQLite，不用 MySQL** | 它是**单文件数据库**：不用单独安装、不用配服务，**但仍然是真正的数据库**（支持 SQL、事务、索引）。 | 交付物要求"双击就能跑起来"，MySQL 要先装服务、配账号密码、建库，多一步就多一个失败的环节。真要换成 MySQL，**改连接方式即可，SQL 基本不用动**。 |
| **后端只用 Node 自带的能力，零新增依赖** | 用的是 `node:http`（写 HTTP 服务）、`node:sqlite`（数据库）、`node:crypto`（密码与令牌），**一个第三方包都没有加**。 | 依赖越少，出问题的环节越少：不用管版本冲突、不用管某个包停止维护。代价见下面"取舍"一栏。 |
| **密码不存明文，用加盐哈希** | 用 `crypto.scrypt` 给密码算一个哈希值存起来，**每个用户一个随机盐**（16 字节）。数据库文件被别人拿到，也**算不出原始密码**。 | 比对时用"定长比较"（`timingSafeEqual`），避免"按响应时间一个字符一个字符猜密码"。 |

**把这些选择说成"只有好处"是不诚实的，代价要一并讲**（这一条讲解时很加分）：

- 没有用 Express 这类后端框架、也没有用 ORM（把数据库操作包装成对象的工具），所以**路由分发、参数校验、建表都要自己写** —— 后端 4 个文件一共约 1481 行，其中相当一部分是这个工作量（连后端的自动化测试也是用 Node 自带的工具写的，同样没加依赖）。
- SQLite 适合"单机、小规模"的场景。它支持事务和索引，能扛住这个项目的规模，但**不适合高并发写入**；真要上线给几百人同时用，第一件要换的就是它。
- 换来的是什么：**双击就能跑、零安装、零依赖、故障面小**，而且所有代码都在自己手里，出问题能一眼看到底。

### 8.3 数据库：一个文件，六张表

数据库就是项目里的**一个文件** `server/data/app.db`（第一次启动时自动建好）。里面六张表：

| 表 | 存什么 | 关键规矩 |
| --- | --- | --- |
| **users** | 用户：用户名、昵称、**密码哈希 + 盐**、角色（普通用户 / 管理员）、是否被禁用、注册时间、**自定义头像**（存图片的 data URL，没设置就是空的） | 用户名唯一；**永不存明文密码**；头像只收图片的 data URL 且正文不超过 200KB，非法的一律拒收 |
| **sessions** | 登录凭证：随机令牌、属于谁、什么时候过期（7 天） | 令牌唯一；每次请求都校验"存在 + 没过期"；退出登录即作废 |
| **algorithms** | 算法元数据：名称、大类、子类、难度、一句话简介、**是否上架**、排序号 | 靠"算法标识"（如 `bubble-sort`）和前端登记表对应；下架的算法前端不显示 |
| **favorites** | 收藏：谁收藏了哪个算法、什么时候 | 同一个人对同一个算法只能有一条 |
| **history** | 学习记录：打开过几次、最多看到第几步、这个算法一共几步、最后更新时间 | 同一个人对同一个算法只留一条，反复看是**累加** |
| **notes** | 学习笔记：用户对自己写的理解 / 易错点（正文最多 2000 字） | 靠"用户 + 算法"两列一起做主键，所以**一个用户对一个算法只有一条**，再写就是更新；**内容清空 = 删除** |

> 一个容易讲错的细节：**算法的代码不在数据库里**。数据库只存"这个算法叫什么、归哪一类、上不上架"这类**说明性信息**；算法本身的代码和步骤生成器仍然在前端（101 个算法，见第一章）。两边靠**算法标识**对应起来。
> 好处是后端不重复维护一份算法清单：第一次启动时，它会从**前端登记表**里把算法导入数据库（实测数据库里就是 101 条，和前端登记表逐条对得上）。
> **⚠️ 这两份清单是手工维护的、必须一起改**：前端加一个算法，后端那份种子也要加一条。这一轮就因为这个栽过一次 —— 动态规划那批只改了前端，于是前端 101 个、数据库还是 98 个，后台列表和统计全对不上；更隐蔽的是后端那份"合法大类"清单里没有「动态规划」，管理员在后台一选它就被 400 拒。经过见《问题与修复记录》六 · 1。

**第一次启动会自动做三件事**：建表；写入一个管理员账号（用户名 `admin`、初始密码 `（已移除的旧口令）`）；把上面那 **101 条**算法元数据**补齐**进数据库。
**⚠️ `admin` / `（已移除的旧口令）` 是给演示用的初始账号，正式使用请在第一次登录后就改掉密码。**
**⚠️ 那个"补齐"是幂等的，也带来一个副作用**：它在每次启动时**只补缺的、绝不覆盖**管理员改过的字段 —— 所以**在后台把某个"种子里的"算法删掉，下次启动它会被补回来**；想永久隐藏请用「**下架**」而不是删除。（详见《问题与修复记录》六 · 1。）

> **后来加字段怎么办？（常被问到这个）** 头像是后来才加的功能，要在已经装了数据的 `users` 表上多一列。
> 做法是**先问一句"这列在不在"，缺了才补一列**（查 `PRAGMA table_info`，然后 `ALTER TABLE … ADD COLUMN`），
> **绝不删表重建** —— 删表重建等于把用户、收藏、学习记录、笔记和后台改过的算法元数据一起清空。
> 这段代码对"新库 / 老库 / 已经升过级的库"三种情况都安全，而且**重复跑也没事**（这叫"幂等"）。
> 证明方式是：一个用例**手工造出一个"上一个版本的老库"**（表里没有这一列、但已经有数据）再让新代码打开它，
> 逐项比对"数据一条没少、值也没变、再跑一次什么都不做"；另外把**真实的数据库复制一份、手动把那列删掉还原成老库**，
> 让新代码升级它，然后**逐列比对内容哈希 —— 前后完全一致**。经过见《问题与修复记录》五 · 9。
>
> **后来加整张表怎么办？** 这一轮新加的 `notes` 用的是**同一招**：`CREATE TABLE IF NOT EXISTS notes (...)` ——
> 新库建它、老库也建它、重复启动多少次都一样，**已有的 5 张表一个字都没动（加 `notes` 之前库里就是这 5 张业务表，现在是 6 张）**；
> 而且因为种子也是幂等补齐的，老库里缺的那 3 个动态规划算法会**顺带自动补进去**，不用任何人删库。
> 经过见《问题与修复记录》六 · 2。

### 8.4 一共 23 个接口

前后端之间只有 23 个接口（都在 `/api` 下面，收发都是 JSON）。分类如下：

| 类别 | 个数 | 干什么 |
| --- | --- | --- |
| **认证** | 4 | 注册、登录、退出登录、查"我现在是谁" |
| **用户功能**（需要登录） | 10 | 收藏的增 / 删 / 查、学习记录的上报与查询、**学习笔记的查 / 读 / 写 / 删**、改自己的昵称和密码 |
| **管理员**（需要管理员角色） | 8 | 后台概览统计、用户列表 / 改 / 删、算法列表 / 增 / 改 / 删 |
| **公开**（游客就能用） | 1 | 取算法元数据（**只返回上架的**），前端用它覆盖本地登记表的显示信息 |
| 合计 | **23** | 见 `server/api.mjs` 末尾的路由表 |

> 笔记那 4 个接口是这一轮新加的：`GET /notes`（列出我的全部笔记）、`GET /notes/:algoKey`（取某一个算法的）、`PUT /notes/:algoKey`（保存或更新）、`DELETE /notes/:algoKey`（删除）。**四个都要求登录，而且只能动自己的数据**；**内容传空就是删除**。

接口的样式统一成一句话：**成功回 `{ ok: true, data: ... }`，失败回 `{ ok: false, error: "给用户看的中文说明" }`**，同时 HTTP 状态码也给对（400 参数错 / 401 没登录 / 403 没权限 / 404 不存在 / 409 重复）。**失败时那句中文会直接显示在界面上**，所以后端写的提示语就是给用户看的文案。

### 8.5 用户能干什么

| 身份 | 能干什么 |
| --- | --- |
| **游客**（不登录） | **和以前完全一样**：看全部 101 个算法、播放动画、上一步下一步、换数据规模、**手动输入数据**、**搜索算法**。点收藏时会弹登录框引导注册。 |
| **登录用户** | 在游客的基础上：**收藏 / 取消收藏**（算法面板标题栏的星标）；**学习记录**（打开过几次、最多看到第几步）；查看「我的收藏」页面（`#/favorites`）；**看自己的学习报告**（`#/report`）；**给每个算法写学习笔记**；改自己的昵称和密码；**换自定义头像**（顶栏那个小圆，没设置就显示昵称首字）。 |
| **管理员** | 在登录用户的基础上：多一个「后台管理」入口（`#/admin`），能管理用户和算法，也能**清空某个用户的头像**。 |

> **学习记录是"节流上报"的**：不是每一步都发一次请求（那样动画一播就会把服务器刷爆），而是大约每 5 步或每 2 秒上报一次，后端把"打开次数 +1、最大步数取较大值"累加起来。

### 8.6 管理员能干什么

后台是一个页面两个标签页（`#/admin`），都是"表格 + 搜索 + 分页 + 新增/编辑弹窗 + 删除二次确认"的形式：

- **概览统计**：用户数、算法数、收藏数、今日新增用户。
- **用户管理**：搜索、分页查看全部用户；改昵称、改角色（普通用户 / 管理员）、禁用 / 启用、重置密码、删除用户。
- **算法管理**：搜索、分页查看算法元数据；新增、修改（名称 / 大类 / 子类 / 难度 / 简介 / 排序号）、删除、**上架 / 下架**。下架之后前端的算法库就不再显示这个算法。

### 8.7 安全规则（这一节最值得讲）

安全规矩一共六条，**每一条都写在代码里，不只是写在文档里**：

1. **密码不存明文。** 数据库里只有哈希值和盐，没有原始密码；登录失败时也**不区分"用户不存在"和"密码错误"**（提示语都是"用户名或密码错误"），免得别人靠提示语猜出哪些用户名是存在的。
2. **权限在服务端查，不是把按钮藏起来。** 管理员的每一个接口，服务器都会**先查这次请求带的令牌对应的人是不是管理员**，不是就直接回 403。前端藏掉按钮只是"界面好看"，真正的门在服务端 —— 拿普通用户的令牌去请求后台接口，一样进不去。
3. **不能删自己。** 管理员删除用户时，如果删的是自己，直接拒掉（避免手一滑把自己删了、当场失去后台权限）。
4. **不能把最后一个管理员删掉、也不能把他降级或禁用。** 否则系统里再没人能进后台，等于把系统锁死。服务器每次都会先数一遍"当前还剩几个可用的管理员"，只剩一个时这两个操作都会被拒。
5. **用户只能碰自己的数据。** 收藏和学习记录一律按"当前登录的人"来查和写，请求里根本不需要（也不允许）传别人的用户编号，所以无法越权看别人的收藏。
6. **改了密码，别的设备就登不上了。** 用户改自己的密码成功之后，这个账号在**其它设备**上的登录会立刻失效（那些设备下次请求会收到"登录状态已失效，请重新登录"），**当前这台设备保持登录** —— 因为用户刚刚用原密码证明了自己是谁，没必要把他自己也踢出去。管理员在后台"重置密码"则是把那个人的会话**全部**清掉（重置的是别人的密码，他本来就该重新登录）。**只改昵称不会影响任何设备**（昵称不是凭据）。这一条是补测试时顺手量出来的不一致，后来回头修掉的，经过见《问题与修复记录》五 · 8。

另外两条工程上的规矩：**所有写接口都校验参数**（用户名 3~20 位字母数字下划线、密码至少 6 位、昵称 1~20 字等），错误提示是中文；**所有 SQL 都用参数绑定**（把值单独交给数据库、不做字符串拼接），从根上防注入。

### 8.9 自定义头像：让用户有个形象，又别把数据库撑大

头像这个功能看起来小，但它把两件工程上的事情讲透了，讲解时很值得说：

**第一件：图片要在"上传之前"就压小。** 用户随手一张手机照片就有 3~5MB，如果直接传原图存进数据库：
数据库一行被撑到几 MB、每次打开页面读"我是谁"都要传几 MB、管理员的后台列表拉十个用户就是几十 MB。
所以选完图**先在这台电脑上处理**：浏览器把图片**居中裁成正方形 → 缩到 128×128 → 导出成 JPEG（质量 0.85）**，出来的通常只有几 KB，
然后才把这张小图传给服务器。这套用的是浏览器**自带**的能力（读文件的 `FileReader`、画图的 `<canvas>`），
**一个图片处理库都没有装** —— 对一个"双击就能跑"的交付物，为了压个图去装一个库不划算。
（**开发时实测**：选一张 **2.84MB** 的手机照片，压缩后上传的 data URL **约 9.7KB** —— 缩小约 **300 倍**。
弹窗里也会把压缩后的大小直接写给用户看，例如"压缩后约 N KB（128 × 128 的 JPEG）"。）

**第二件：服务器不信任前端。** 前端压过了，不代表服务器就该照收。头像这个字段会被**原样塞回网页的 `<img>` 标签里**，
所以它必须被限制成"只能是一张图片"：

| 规矩 | 内容 | 为什么 |
| --- | --- | --- |
| 只收图片的 data URL | 必须形如 `data:image/png;base64,…`（允许 PNG / JPEG / JPG / WebP / GIF） | 这个值会进 `<img src="…">`，随便存字符串等于给别人开了一个存恶意内容的地方 |
| 正文必须是合法 base64 | 不能把网页代码塞在图片数据的位置 | 上面那条只看开头，这条看内容 |
| 正文不超过 200KB | 前端压完只有几 KB，这条挡的是"有人绕过前端直接塞几 MB" | 防止把数据库和接口拖垮 |
| **不收 SVG** | `data:image/svg+xml` 直接拒绝 | SVG 里能内嵌脚本，同源下就是一个 XSS 载荷 |
| 传空 = 清除 | 传 `null`（或 `''`）表示**清除头像**，恢复成昵称首字 | 这是合法操作，不是错误 |

**非法内容一律回 400 + 中文说明，而且一个字都不写进数据库** —— 这一条有专门的用例（含"库里没被写进去"的断言）。

**第三件（也可以讲）：给已经在用的数据库加一列，怎么不丢数据。** 头像需要给 `users` 表加一列，
而用户已经在用的库里有真实数据，**不能删表重建**。做法是**先查这一列在不在、缺了才补一列**（`ALTER TABLE ADD COLUMN`），
新库 / 老库 / 已升级的库都走同一条代码路径，重复跑也没事。完整经过见《问题与修复记录》五 · 9。

## 第九章 · 这一轮新加的五个功能

这一章讲最近一次一口气加进去的 5 个功能（动态规划、学习报告、算法搜索、手动输入数据、学习笔记）。
讲解时可以**挑两个讲**（推荐"动态规划"和"学习报告"），其余作为"还做了什么"快速带过。

### 9.1 动态规划：给平台补上第 10 个大类

**加了什么**：三个经典算法 —— **0-1 背包**、**最长公共子序列（LCS）**、**编辑距离**，难度都是"较难"。
它们落在两个新的子类里：「背包问题」1 个、「双串模型」2 个。大类位置在「**图**」之后、「**查找**」之前 ——
因为动态规划在教材里属于"算法设计方法"那一章，排在数据结构（线性表到图）之后、查找排序之前最自然。

**为什么它值得单独讲：它证明了这个平台"加一种新东西"真的不用改核心代码。**

原来在缺口清单里，这一条我写的是"**需要再加一个二维表格渲染器**"。真动手时才发现：**不用加**。
动态规划做的事就是"填一张二维表"，而这正是**画矩阵时用的那一套**（通用格子板 + 命名指针），
所以这三个算法直接声明用现成的画法就行 —— **一个渲染器都没新增**，注册表里的画法仍然是那 **6 种**。
设计口径：**"缺口清单里'需要再加一个 X'往往是估的 —— 动手前先看一眼现成能力能不能覆盖。
这次省下来的不只是一个渲染器，而是一整套新的回归测试。"**

**画面上看得见什么**（这是动态规划难讲的地方，界面把它变成了看得见的）：

| 表上的样子 | 意思 |
| --- | --- |
| 第 0 行、第 0 列颜色偏暗 | 那是**边界**（不放任何物品 / 空串），值都是 0 |
| 紫色高亮的格子 | **这一步正在算的格子** `dp[i][j]` |
| 红色高亮的格子 + 指针对着它 | **这一步用到的来源格子** —— 指针上直接写着是哪种操作（"不放 / 放"、"上 / 左"、"删 / 插 / 换"） |
| 绿色 | 已经算好的格子 / 选中的物品 |
| 格子右下角的小字 | 它的 `i, j`，方便对着代码里的公式核 |

因为**当前代码行**和**当前高亮的格子**来自同一帧数据（第四章那条核心机制），
所以讲到哪一行代码，表上对应的那一格一定同时亮起来 —— 这是这个功能最直观的看点。

### 9.2 学习报告：把学习记录画成图（图是手画的）

**加了什么**：新页面 `#/report`「我的学习报告」，从顶栏右侧进。页面上有五块：
**覆盖率环**（学过多少个 / 一共 101 个）、**按 10 个大类的分布条**、**打开次数 Top 10**、
**最近学习**、**看得最完整的几个**。

**这一节最值得讲的是两件事：**

**第一，图全是手画的，没有引入任何图表库。** 那个覆盖率环就是一个 **SVG 圆**，靠"虚线的长度"
表达百分比；大类分布的那些条是 **CSS 的宽度百分比**。所以这一页**零新增依赖** ——
和"后端零新增依赖""头像压缩零新增依赖"是同一条思路。
设计口径：**"我需要的只是'一个环 + 几条横条'，为它引入一个几百 KB 的图表库不划算；
而且手画的好处是配色和整个平台的图例是同一套。"**

**第二，页面上每一个数字都由一个"不碰界面"的纯函数算出来。**
算法是这样的：后端只提供原始的学习记录（打开过几次、最多看到第几步、这个算法一共几步、最后什么时候看的），
这些原始数据加上**前端的算法登记表**（一共几个算法、每个属于哪个大类），
一起交给 `src/core/report.ts` 里的纯函数 `computeReport()`，它算出页面上全部数字；
`ReportView.vue` 只负责"怎么画"。这就是第四章讲的**分层**在功能上的直接落地 ——
**"算得对不对"和"画得好不好看"是两件可以分开查的事**：改口径不用碰图，改图不会动口径。

**口径必须说清（常被问到"什么算学过"）**：

| 口径 | 规则 | 为什么要这么定 |
| --- | --- | --- |
| **学过** | 至少要看到**第 2 步** | 第 1 步是初始帧，**打开就算看过**的话，随手点开 20 个算法覆盖率就虚高了 |
| **覆盖率** | 学过的算法数 ÷ **算法登记表里的总数（101）** | 分母只认"真正能点开学的算法" |
| **完成度** | 看到第几步 ÷ 一共几步，**超过 100% 按 100% 记** | 步数口径以后若有变化，不至于画出 120% 这种荒唐结果 |
| 后台加的那些算法 | 可以出现在「最近学习」里，但**不算进覆盖率** | 它们只有元数据、没有代码，前端点不开 |

### 9.3 算法搜索：跨大类找算法

**加了什么**：算法选择器顶部多了一个搜索框，**跨全部大类**模糊搜算法的**名称和 id**，
命中的字会被标出来，按 ↑ ↓ 选、**回车直接打开**、Esc 第一次清空搜索、第二次才关面板。

**为什么加**：算法到 101 个之后，"知道名字、但记不住它在哪个大类"变成了一件很费事的事 ——
以前必须先想"编辑距离算算法设计方法还是字符串处理"，再一层层点进去。

**工程上的做法**（一句话）：搜索逻辑放在纯函数 `src/core/algorithmSearch.ts` 里，
只做"给我一个查询串、还你一串命中结果"，**不认识界面**；组件只负责把结果画出来。
所以"搜索准不准"可以脱离浏览器单独验。快捷键那几个行为（↑ ↓ 回车 Esc）则是组件里的事。

**一处刻意的取舍（提示怎么给）**：搜索框**不放 placeholder 灰字** —— 框前已经有一个 🔍 图标、
输入框上也保留着 `aria-label="搜索算法"`，提示的职责由这两样承担。
原来那段很长的灰字（"跨全部大类搜索算法名称或 id……"）**已经去掉**：
它把本来就不宽的输入区挤掉一半，而它想说的内容在图标、无障碍标签和面板标题里都已经有了。
> 顺带一句可以讲的道理：**提示文字也是界面的一部分，重复的提示不是"更保险"，只是更挤。**
> 保住 `aria-label` 是因为读屏软件靠它，灰字靠不住 —— 去掉灰字的同时**没有动无障碍标签**。

### 9.4 手动输入数据：用自己的数据喂算法

**加了什么**：顶栏多了一个 **✏️** 按钮，弹窗里可以自己敲一串数字（例如 `5, 2, 9, 1, 7, 3`）喂给当前算法。

**为什么加**：在这之前数据来源只有"示例 / 随机 + 规模"三种，**没法验证自己心里想的那个例子** ——
而这恰恰是学习算法时最常做的事（"如果数据是逆序的会怎么样？"）。

**做的时候有两条讲究**（外加一处**已经去掉**的东西）：

1. **校验是独立的一层**：个数必须 **2~12**、每个值必须 **1~999**，非法输入给**中文**提示。
   规则写在纯函数 `src/core/manualInput.ts` 里（不碰界面），所以能单独核对。
   设计口径：**"不能把用户敲的字符串直接塞给算法 —— 界面上任何一个能输入的框，都是攻击面，
   也都会变成 bug 的来源。所以先过一层校验，这一层还是个纯函数，顺带就能被测试。"**
2. **走的是同一条路**：合法数字拿到之后，和内置的示例 / 随机数据走**完全相同**的那条
   "生成步骤序列"的路径 —— 没有为手动输入单开一条代码分支，所以手动输入出来的动画，
   和随机数据的动画受同一套强制校验保护。
3. ⚠️ **已经去掉的那个可点「示例」按钮**（这是本次校订记下来的一处小改动）：
   弹窗里原本还有一个小按钮「示例：`5, 2, 9, 1, 7, 3`」，点一下会把这串数字**塞进输入框**。
   去掉它的理由有两条，都很实在：① 示例在同一个弹窗里**本来就出现两次**（顶部提示的"例如：…"、
   输入框的 `placeholder`），第三个入口纯属重复；② 它**会覆盖用户已经敲进去的内容** ——
   用户只是想先看看格式，点一下就把自己写的数据弄没了。现在示例**只作展示**，弹窗里只剩
   「用当前数据」一个快捷按钮。设计口径：**"能点的东西必须明确比不点更好；一个只会覆盖用户输入的按钮，
   不如没有。"**（这一条没有自动化用例 —— 它是纯界面取舍，靠人眼核对；这一类的"还剩下什么"记在 `开发进度与交接.md` 第五节。）

### 9.5 学习笔记：一个算法一条

**加了什么**：**左栏、代码框的正下方**多了一块「📝 学习笔记」面板（和代码框同宽、同在左栏，所以**不占右边动画区的高度**；面板整体上限 32vh、输入框 56px~18vh，超出由面板内部滚动），
登录后可以给**当前这个算法**写一段自己的话（理解、易错点、调试心得），正文最多 2000 字。

**后端这一轮加的是新表 + 4 个接口**（见 8.3 / 8.4），有两条行为**必须讲清楚**，因为它们是由**表结构**决定的：

| 行为 | 为什么 |
| --- | --- |
| **一个用户对一个算法只有一条笔记** —— 再写一次是**更新**，不是新增第二条 | 这张表的主键就是"**用户 + 算法**"两列，不是自增编号。所以"重复写"在数据库层面就不可能发生，**不是靠界面自觉** |
| **把内容清空再保存 = 删除这条笔记** | 用户想"撤销"时最自然的动作就是清空。存一条空字符串会让列表里出现一条点不开的空笔记，不如直接删掉 |

**另外两点**：① **笔记是私人数据** —— 换一个账号的令牌去读、去改、去删，服务器一律拒绝，
这一条有自动化用例盯着；② **加这张新表没有动老数据** —— 用的是 `CREATE TABLE IF NOT EXISTS`，
新库建、老库也建、重复启动多少次都一样，**已有的 5 张表一个字都没动（加 `notes` 之前库里就是这 5 张业务表，现在是 6 张）**（见 8.3 与《问题与修复记录》六 · 2）。

### 9.6 这一轮还顺手对齐了一处"没人负责的数字"

5 个功能是**分几块并行**做的。其中动态规划那一块**只改了前端** —— 于是前端说 101 个算法、
后端数据库里还是 98 个：后台的算法列表、管理员概览里的算法数、公开接口返回的元数据，全都和后端差 3 条；
更隐蔽的是后端那份"**合法大类**"名单里没有「动态规划」，管理员在后台一选它就被 **400** 拒。

**根因不是谁的代码写错了** —— 写前端的人当然把登记表加对了，写后端的人当然把自己的种子维护得没问题，
问题在于"**这两端是否一致**"这件事**既不属于前端的活、也不属于后端的活，于是它就不属于任何人**。
修好之后我做的验证是**逐条对齐**：前端登记表 101 == 数据库 101，两边算法标识的**集合与顺序完全一致**，
名称 / 大类 / 子类**零处不一致**；新增「动态规划」类的算法也从 **400 变成了 200**。
完整经过见《问题与修复记录》**六 · 1**（这是讲解时"真实工程感"最强的一个故事）。

## 第十章 · 质量保证：933 项自动化测试（前端 831 + 后端 102）

讲解时可以说："我没有靠肉眼看动画或者手工发请求来判断对不对，我写了 933 项自动化测试 —— 前端 831 项管算法，后端 102 个用例管接口，一条 `npm test` 前后端一起跑。前面那 722 项是**对注册表里每一个算法各跑一遍**的，以后新增算法，规则自动生效，不用重复写测试（这一轮加了 3 个动态规划算法，前端测试就从 704 涨到 722 —— **一条新断言都没写，是已有规则自动套到了新算法上**；后来补到 734 项）；另外**新增的 6 项**是我拿用户报的一个 bug 换来的**回归用例**（"进学习默认选中算法、系统又把这次默认进入算了一次学习"，经过见《问题与修复记录》）：这类 bug 只会在数据库里多出一条看不见的记录，界面上毫无异常，所以必须留一条会自己跑的断言看着它。后端那 102 个用例跑在**临时数据库 + 随机端口**上，跑测试不会动到真实的数据库文件。"

**校验规则是按数据结构区分的**，因为不同数据结构的不变量本来就不一样：数组要求"长度恒定 + 多重集守恒"，顺序表允许长度变化但不得超过容量，链表则校验 next / prev / 头指针 / 命名指针的引用是否全都指向真实存在的结点；树校验孩子 / 双亲 / 线索的引用自洽且从根能走遍所有结点，图校验顶点 id 唯一、边与高亮指向的顶点真实存在、顶点坐标落在 0..1 之间。

测试覆盖的内容（用大白话）：

| 测试项 | 它保证什么 |
| --- | --- |
| 数组类排序的终态严格升序；堆的终态是合法的大根堆（父 ≥ 子）；二叉排序树 / AVL / 红黑树的终态中序严格升序；外部排序的记录一个不多一个不少 | 算法没写错（"有序"在数组、堆、树上本来就不是一回事，所以分成好几套判据） |
| B 树 / B+ 树：一个结点里的关键字有序、孩子数正好比关键字多一个、所有叶子在同一层、从根能走遍所有结点 | 多路树**不是二叉树**，不能拿"中序升序"去卡它，得按多路树自己的性质验 |
| 数组类的每一步长度都不变，顺序表每一步都不超过容量 | 没有数据丢失 |
| 起始帧严格等于输入数据 | **没有发生"历史记录被覆盖"这个致命错误** |
| 每一步都是独立的快照对象 | 同上，用另一种方式再验一遍 |

| 每一步的解说词都不为空 | 不会出现空白解说 |

| 切换算法 / 换数据规模都会正确重算并归零 | 状态切换不出错 |

跑法：`npm test`（前后端一起，933 项）或 `npm run test:server`（只跑后端那 102 个用例）。

## 第十一章 · 可扩展性：加一个新算法只要两步

1. 新建一个文件，写出这个算法的源码字符串，并写一个"步骤生成器"（每一步告诉系统：对应第几行、现在数据什么样、在做什么动作）。
2. 在算法注册表里加一行。

**播放器、代码面板、柱状图、控制栏全都不用动。** 这是为了满足需求文档中"新算法以配置/插件形式接入，无需改动核心播放器"的要求。

如果行号标错了、忘了拷贝快照、解说词忘了写，测试会立刻报错——**扩展不会以牺牲正确性为代价**。

> **⚠️ 但"两步"只说了前端这一半。** 后端还内置了一份**算法元数据种子**（名称 / 大类 / 子类 / 难度 / 简介），
> 前端是 `.ts`、后端是 `.mjs`，**运行时谁也读不到谁**，所以**加算法要"两边都加"**：
> 前端注册表加一行，后端种子里也补一条。这一轮就因为这个栽过一次 —— 动态规划那批只改了前端，
> 于是前端说 101 个、数据库里还是 98 个，后台列表 / 统计 / 公开接口全对不上；
> 后端那份"合法大类"名单里也忘了加「动态规划」，管理员在后台一选它就被 400 拒。
> 修好之后的验证是**逐条对齐**：两边条数相等、算法标识的集合与顺序完全一致、名称 / 大类 / 子类零处不一致。
> 教训是：**并行开发时，"跨两端的那个数字 / 那个枚举"是没人拥有的** —— 收尾必须专门有人对齐一次。

## 第十二章 · 常见问题与应答

**Q1：所谓"绝对同步"，你怎么证明？**
A：因为高亮行号和画面数据**不是两个东西**，而是同一个步骤对象里的两个字段。第 N 步的 `line` 和第 N 步的 `array` 是同一次记录写进去的，不存在其中一个更新了另一个没更新的时间窗口。这不是"同步得好"，而是"结构上无法不同步"。

**Q2：上一步是不是把算法重新执行了一遍？**
A：不是。算法在页面打开时就一次性执行完，所有中间状态都存下来了。上一步只是把"当前第几步"这个数字减 1，界面自动重新推导。所以是瞬间完成，而且结果和当初正向走到那一步时完全一致，这一点有测试保证。

**Q3：为什么"当前高亮哪一行"不做成一个可以单独赋值的变量？**
A：因为只要能单独赋值，就有"改了步骤忘了改行号"的可能。我把它做成只读的计算结果——它只能由"当前第几步"算出来，没有第二个入口。少一个可写状态，就少一整类 bug。

**Q4：如果算法里有随机性（比如快速排序随机选基准），会不会乱？**
A：步骤序列在页面打开时就一次性算完并固定下来，之后所有操作都只读这份序列，所以随机性不会影响回退的一致性。如果需要每次打开都一样，再给随机数发生器固定一个种子即可。这是下一步的扩展点。

**Q5：一万步会不会卡？**
A：步骤序列用的是"浅层响应式"，不会对几千个步骤对象做递归代理；当前演示的算法默认数据下每步序列是 4~90 格（最长的是"堆排序"的 90 格），实测切换无延迟。若真做到上万步，下一步的优化是分段加载（需求文档里也预留了这条）。这是已知的性能上限，我在文档里做了标注。

**Q6：为什么要用 Canvas 画柱子，不用普通的 HTML 元素或 SVG？**
A：柱状图数量多、每帧都要重画。用 Canvas 直接画像素，12 根柱子每帧重画的开销可以忽略；如果用 DOM 元素，每一帧要改几十个节点的样式，数量一多就会掉帧。另外 Canvas 更容易精确控制像素级的效果（比如柱子顶部的圆角、数值标注）。

**Q7：D3 到底用在哪了？**
A：用在"数值 → 屏幕坐标"的换算上（`d3-scale`）。比如把数值 0~99 映射到像素高度，把第 i 根柱子分配到水平方向的第几个槽位。这部分数学交给经过充分验证的成熟库，避免自己推导出错。**没有用 D3 的动画功能**，因为 D3 的动画是"发射后不管"的，用户中途点"上一步"会产生两个动画同时改同一批柱子，画面会失控。所以动画时钟由我自己用 `requestAnimationFrame` 控制。

**Q8：插入排序演示时，为什么中间会短暂出现两个一样的数字？是不是 bug？**
A：不是 bug，这是插入排序的**真实中间状态**。插入排序的做法是"把当前元素拿出来暂存在一个变量里，然后把前面比它大的元素逐个往后挪一格，腾出位置再放回去"。在"挪"到"放回去"之间的那一瞬间，被拿出来的那个值只存在于变量里，数组上就留下了一个空位，看起来就是某个数字重复了一次、另一个数字暂时消失。
我们的可视化**忠实反映了这个状态**，而且专门写了一条测试把这个行为固定下来——防止以后有人误以为它是 bug 而"修掉"。如果不想展示这个中间状态，可以只在"放回去"之后记录一步，但那样就看不到"腾位置"这个过程了。

**Q9：为什么不用 React？**
A：这个项目的技术栈选型是 Vue 3。就本项目的需求而言，两者都能实现，核心的同步机制（生成器 + 步骤序列 + 唯一光标）是与框架无关的纯 TypeScript 代码，换成任何框架都不需要改动。选 Vue 的原因是中后台类页面的开发效率高、中文资料充分。

**Q10：你怎么保证加新算法不会破坏同步？**
A：三层保险。第一，算法只能通过"注册表"接入，接口固定，它拿不到界面，也没有能力直接改界面状态。第二，引擎有一道强制校验：行号越界、指向空行、快照被覆盖、元素丢失、下标越界，任何一种都会立刻抛错，而不是默默显示错误内容。第三，933 项自动化测试（前端 831 + 后端 102）会对每一个已注册的算法跑一遍全部规则（前端那 734 项就是干这个的，另外还另有 6 项盯着"进入学习不默认选中算法"这条线），后端那 102 个用例则盯住接口的权限、校验、笔记的数据隔离与头像的安全规则。

**Q11：这个项目有什么不足、下一步做什么？**
A：诚实地说有**四点**，其中两点是"这一轮刚补上的"，另两点是真缺口：① **规模**：目前实现 **101 个算法 / 10 个大类**（线性表、栈、队列、数组与矩阵、串、树与二叉树、图、**动态规划**、查找、排序），已经超过需求文档里规划的 40 个，但接入成本已经被压到"写一个文件 + 注册一行"——加 16 个算法（排序 11 个 + 查找 5 个）时核心的播放器、代码面板、控制器、选择器**一行都没有改**；这一轮加动态规划那 3 个也一样，**连渲染器都一个没加**（直接复用了画矩阵那套二维表格画法）；② **渲染器**目前有六种（柱状图 / 单元格表格 / 结点箭头图 / 通用格子板 / 树形图 / 网络图），覆盖了线性结构、栈队列、矩阵、树、图**和动态规划**，其中柱状图 / 树形图 / 网络图三种支持"主视图 + 下方板子"，通用格子板还支持网格布局；③ ✅ **~~数据输入只有"随机 / 示例 / 规模"~~ → 这一轮补上了手动输入数据**（个数 2~12、每个值 1~999，校验在纯函数里，非法输入给中文提示），但**导入 / 导出文件仍然没做**（也没有把步骤序列导出成图片或分享链接）；④ **用户系统和管理员系统已经做完了**（注册登录、收藏、学习记录、学习报告、学习笔记、后台的用户管理与算法管理），但它是"够用的最小实现"，还有明显的边界：没有找回密码、没有邮箱验证、没有登录失败次数限制，数据库是本机单文件（**不适合高并发**，要上线给几百人同时用，第一件要换的就是它），后台也还没有操作日志。
下一步按需求文档的里程碑推进：先补手动输入与导入导出，再补动态规划类算法，然后是把用户系统往"学习闭环"上做（学习进度可视化、排行榜），以及后端的安全性加固（登录限流、密码找回）。

**Q11-A：为什么不干脆不用后端，把收藏存在浏览器里？**
A：因为**用户数据不能只存在浏览器里**。收藏和学习记录如果存在浏览器本地，换台电脑、换个浏览器、清一次浏览器数据就全没了；而且管理员要能看到全体用户，这不可能靠散在每个人浏览器里的数据拼出来。更关键的是**权限判断只能在服务器上做**：如果"我是不是管理员"由浏览器说了算，那谁都能改自己浏览器里的数据冒充管理员。所以这一部分必须放到服务器上。

**Q11-B：为什么数据库用 SQLite 而不是 MySQL？后端为什么不用现成的框架？**
A：SQLite 是**单文件数据库** —— 不用单独安装、不用配服务，**但它是真正的数据库**（支持 SQL、事务、索引）。我的交付物要求"双击就能跑起来"，MySQL 要先装服务、配账号密码、建库，每多一步就多一个演示当天出问题的环节；真要换 MySQL，改连接方式即可，SQL 基本不用动。后端也没用 Express 这类框架：Node 自带的 `node:http` / `node:sqlite` / `node:crypto` 就够了，**整个后端一个第三方包都没加**，依赖越少出问题的环节越少。
**代价我也说清楚**：没有框架和 ORM，路由分发、参数校验、建表都要自己写（后端 4 个文件约 1481 行，相当一部分是这个工作量）；而且这个后端是**单机、低并发**的定位，不适合生产环境的高并发写入。换来的是零安装、零依赖、双击就能跑、故障面小。

**Q11-C：你怎么保证普通用户进不了后台？**
A：**权限在服务端查，不是把按钮藏起来。** 管理员的 8 个接口，服务器每次都会先看请求带的令牌对应的人是不是管理员，不是就直接回 403 —— 前端把"后台管理"入口藏掉只是界面好看，真正的门在服务端。演示时也可以反着验：拿一个普通用户的登录令牌直接去请求后台接口，服务器照样拒绝。另外还有两条防止"把系统锁死"的规则：管理员**不能删自己**，也**不能把最后一个管理员删掉、降级或禁用**（只剩一个时这两个操作都会被拒）。

**Q12：界面上展示的是 C++ 代码，可你们系统是用 TypeScript 写的，这两个是什么关系？代码真的被执行了吗？**
A：要说清楚两件事。

第一，**界面上那份 C++ 代码是"给人看的展示代码"**，用的是《数据结构》教材通用的写法（`void bubbleSort(int a[], int n)`），因为学生的教材和考试都用 C++，配色和语言风格也照 C++ 来。它不会被浏览器执行。

第二，**真正产出步骤序列的是一段等价的 TypeScript 生成器**。它和展示的 C++ 逐行对应：C++ 的每一次比较、每一次交换，在生成器里就是一个 `yield`，并且带上"这一动作对应 C++ 源码的第几行"。所以真正被执行的是生成器，而界面显示的、被高亮的是 C++。

这是这类算法的标准做法。因为要在浏览器里显示 C++ 的**每一步**，需要把 C++ 编译成 WebAssembly 并做单步调试接口，工程量远超这个项目的范围；而"按同一算法逻辑产出一份带行号标注的步骤序列"能百分之百达到同样的教学效果。

第三，也是关键的一点：**"生成器里的行号"和"C++ 源码的行号"是否一致，不靠人工保证，而是机器强制的**。引擎在生成步骤序列时会做校验：行号必须在 1 到代码总行数之间、必须落在一个非空行上，任何一条不满足就直接抛错、页面报错，而不是默默显示一个错误的行。再加上前端那 831 项自动化测试（其中 734 项对每个算法都跑一遍，另外 6 项守着"默认进入学习不算一次学习"），所以两边不可能悄悄错位。

**Q13：为什么高亮行不直接用参考图里的亮青色？**
A：因为要求高亮行的代码显示为**亮白色**。亮青色 `#33CCCC` 的亮度很高，白字压在上面对比度只有 1.97:1，而国际无障碍标准（WCAG）对正文要求至少 4.5:1 —— 也就是说那样配会看不清。所以我把底色压深到同一色系的深青 `#116A6E`（对比度约 6.3:1，达到 AA 级），左侧保留一条 `#33CCCC` 的亮青竖条，视觉上仍然是"青色系 = 正在执行"，但白字清晰可读。这是一个"美观"与"可读性"之间的取舍，我选择了保证可读。

**Q14：查找算法的"目标值"是怎么定的？会不会出现找不到、或者折半查找算错的情况？**
A：分三点说。

第一，**目标值由算法自己声明**。每个查找算法提供一个 `defaultTarget` 方法，从当前数据里挑一个**确实存在的值**，所以演示时一定能命中，不会出现"演示了半天结果是没找到"的尴尬。这个值会显示在两处：图上的橙色虚线（"目标值 9"）和底部变量栏的 `target = 9`。

第二，**折半查找必须先有序，这件事由框架强制保证**，不靠用户自觉。算法声明了一个 `prepareData` 方法，载入数据时（包括点「随机数据」）会先执行一次排序再交给算法。所以用户随便怎么换数据，都不可能把一个无序数组喂给折半查找 —— 这是把"算法前提条件"做进了接入规范里，而不是写在注释里等人遵守。

第三，**"找不到"的分支代码是完整的、但没有被演示**。两个查找算法的源码里都有 `return -1`，生成器里也写了对应的收尾步骤（解说"查找失败：数组中不存在 target"）。只是因为目标值一定取自数组本身，这条分支在演示中不会走到。这是我有意做的取舍：保证演示稳定。如果后续加上"手动指定目标值"的输入框，这条分支自然就会被用到。

**Q15：链表和顺序表的不变量完全不一样，你怎么用同一套框架管住它们？**
A：这正是我特意做的一件事：**校验规则按数据结构类型区分**。

- **数组**（排序 / 查找）：长度恒定、终态多重集守恒、首帧必须等于输入（防快照别名）。
- **顺序表**：长度会因插入删除变化，所以不要求长度恒定，但要求"任一时刻元素个数不超过容量"，并且声明的表长不能大于实际存储的元素个数。
- **链表**：校验结构自洽 —— 头指针、每个结点的 next / prev、命名指针、遍历顺序，指向的结点 id 必须真实存在；另外校验"数据序列里的每个值都能在链表上找到"。
- **通用格子板**（栈 / 队列 / 矩阵 / 堆 / 字符串匹配 / 哈希表）：只查一条硬约束 —— 板子上的指针、连线和纸带游标必须指向真实存在的格子。
- **树**：结点 id 唯一，孩子 / 双亲 / 线索 / 命名指针指向的结点必须存在，而且从根出发要能走遍所有结点（否则画面上会凭空少几棵子树）；二叉树走 `left` / `right`，一个结点装多个关键字的 B 树 / B+ 树走 `children`。
- **图**：顶点 id 唯一，边的两端、高亮、已访问、badge 指向的顶点都必须存在，顶点坐标必须落在 0..1 之间（不然会画出面板外面）。

算法在注册时声明自己属于哪一类（`renderer: 'array' | 'seqlist' | 'linked' | 'scene' | 'tree' | 'graph'`），引擎就套用对应的规则。这比"一套规则管到底"严谨得多，也是这套框架能同时容纳六种可视化形式的根本原因。

**Q16：双链表插入的时候，中间有几帧看起来指针是"矛盾"的，是不是画错了？**
A：不是画错，是**真的矛盾**，而且这正是双链表教学里最该讲清楚的一点。

双链表插入要改 4 根指针，而**指针的修改不可能是原子的** —— 无论按什么顺序改，中间一定会出现"前驱的 next 已经指向新结点了，但新结点的 prev 还没指回来"这类短暂的不一致状态。

所以我最初写的测试"要求每一帧 prev / next 都完全自洽"是**错的**，它跑不过；我把测试改成只校验**收尾帧**，并在测试里写明了原因。这也反过来印证了教材上反复强调的那句"顺序不能乱"：虽然中间态一定不一致，但按 `① s->next = p->next; ② p->next->prev = s; ③ p->next = s; ④ s->prev = p` 这个顺序改，**任何时候都不会把链表后半段弄丢**，这是可以保证的。

**Q17：链表里"还没接到链上的新结点"是怎么画出来的？**
A：这是实现时踩到的一个真问题。按常规做法，渲染时是从头指针沿 next 走一遍、把走到的结点按顺序画出来。但"刚 new 出来、还没插进链表"的新结点是走不到的 —— 结果就是那一步画面上什么都不发生，而解说却在说"申请新结点 s"，非常割裂。

解决办法是给结构快照同时记录两串：`reachable`（从头指针真的走得到的）和 `order`（渲染顺序 = reachable + 还没接上链的游离结点）。游离结点会先画在最右边，插进去之后就"跳"到它该在的位置。箭头也只画真实存在的指针（因为游离结点之间并没有连线），否则会画出一条不存在的箭头。

顺带还修掉了一个由此引发的 bug：判断"链表是否成环"原来取的是渲染序列的最后一个结点，而那个结点可能恰好是游离结点 —— 于是双链表插入的中间帧会误画出一条绿色的环箭头。改成只看 `reachable` 这一串之后就正确了。

## 第十三章 · 术语表（给非技术读者的解释）

| 术语 | 大白话解释 |
| --- | --- |
| **生成器（Generator）** | 一种可以"执行到一半暂停、把控制权交出来、之后再从原地继续"的特殊函数。算法用它来"每做完一个动作就喊一声停"。 |
| **步骤序列（Trace）** | 算法执行过程中每一步的完整记录，本项目里就是一个数组，默认数据下从 4 格到 90 格不等。 |
| **快照（Snapshot）** | 某一刻数据的完整拷贝。强调"拷贝"是因为如果只记录"指向数据的指针"，数据一改历史就全毁了。 |
| **声明式 / 派生** | 不直接去改界面，而是改"唯一的状态"，界面自己算出该显示什么。 |
| **单一真相来源（SSOT）** | 全系统只有一个地方存真实数据，其他地方都是它的投影。 |
| **O(1)** | 计算机术语，表示"耗时固定，不随数据量增长"。这里用来形容"上一步"是瞬间完成的。 |
| **纯函数** | 给定同样的输入必然得到同样输出、且不产生副作用的函数。本项目里"画柱子"就是纯函数——给它第 N 步的数据，它画出第 N 步的样子。 |
| **Canvas** | 浏览器提供的一块"画布"，可以用代码在上面直接画图形。 |
| **前端 / 后端** | 前端 = 跑在用户浏览器里的那部分（页面、动画）；后端 = 跑在服务器上的那部分（存数据、判权限）。本项目两边都有，叫"前后端分离"。 |
| **数据库（SQLite）** | 专门用来存数据的软件。本项目用的 SQLite 特殊在：**整个数据库就是一个文件**，不用安装、不用配服务。 |
| **哈希（加盐哈希）** | 把密码"搅碎"成一串看不出原文的字符再存起来，而且每个用户额外掺一点随机字符（盐），所以两个人用同样的密码，存出来的结果也不一样。 |
| **令牌（Token）** | 登录成功后服务器发的一张"临时通行证"（一串随机字符），之后每次请求都带上它。它有有效期（本项目 7 天），退出登录就作废。 |
| **接口（API）** | 前端和后端之间约定好的"说话方式"：前端按固定格式问，后端按固定格式答。本项目一共 23 个接口。 |
| **权限校验** | 判断"这个人有没有资格做这件事"。本项目在**服务器上**判断，不在浏览器里判断（浏览器里的判断可以被改掉）。 |
| **data URL（图片的 data URL）** | 把一张图片的全部内容直接写成一行文字（形如 `data:image/jpeg;base64,…`）的做法。优点是能直接塞进网页的 `<img>` 里、不用另存成文件；缺点是**越大越占地方**，所以头像要先压到 128×128 再存。 |
| **幂等（升级）** | 同一个操作执行一次和执行多次，结果一样、都不出错。本项目给数据库加列就做成幂等的（先查这一列在不在，缺了才加），所以"新装的机器"和"用户手上那台老机器"走的是同一条代码路径，重复启动也不会出事。 |
